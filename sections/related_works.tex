\section{Related Work}\label{sec:related}
%% ============================================================

Validation of formal hardware models is important, as the validity of verification results depends on their accuracy~\cite{reid2016trustworthy,armstrong2019sail,reid2016isaf}; bugs in this environment specification are not isolated occurrences~\cite{Fonseca:2017:EnvironmentBugs}.
Prior work focused on the semantics of the instruction set architecture by validating a formal description against real hardware~\cite{reid2016trustworthy,reid2016isaf, armstrong2019sail}. This enables the construction of verified interpreters of machine code and the reasoning about instructions.

Another line of work focuses on understanding the ARM's weak-memory model~\cite{alglave2011litmus,alglave2014herding} or the TSO model of x86~\cite{owens2009x86tso,sewell2010x86tso}. 
Their work uses Litmus tests to validate their memory model against real hardware, testing the hardware-permitted orderings of memory accesses.
However, none of these works explicitly include the internal microarchitectural steps and focus only on the directly visible outcome of the memory accesses. Our work also includes the interactions with the memory management unit and page table updates.

IronSpec~\cite{goldweber2024ironspec} explored debugging specifications to determine whether developer intent matches the specification, using mutation testing and other techniques. This work focuses on software specifications while we explore validating a hardware model. 
TraceLink~\cite{Hackett:2025:Tracelink} checks whether an execution trace of a program matches its state machine specification. However, it requires all events to be present, while we need to handle hidden events.
Velosiraptor~\cite{Achermann:2025:Velosiraptor} applies software synthesis to generate programs that configure the page table, but does not validate whether the specification itself is correct.
