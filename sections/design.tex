\section{Design}\label{sec:design}
%% ============================================================

\autoref{fig:validation-pipeline} shows the overview of our model validation pipeline.
The goal is to systematically validate the hardware model against real hardware. 
The validation pipeline consists of a test-case generator, a test execution harness, and a trace validator. 
The pipeline's input is a reduced hardware model that serves as the basis for generating test programs and validating traces.

\noindent\textbf{Problem Definition.}
Given a hardware model, generate a set of test cases that cover hardware behaviors that we intend to observe, execute the test cases, and for each test, identify whether the output is allowed by the model.
Refine the model if there is a mismatch.

Next, we describe the purpose of each component in the validation pipeline.

\noindent\textbf{Hardware Model.} 
%
The hardware model is the part of the system we want to validate. \hl{While our high-level methodology extends to most hardware models, for our discussion we specifically consider} an x86 multi-core processor with its MMU modeled as a state machine with transitions for \emph{observable} program steps (e.g., memory accesses, barriers, TLB invalidations) and for \emph{internal} hardware events (e.g., a TLB eviction, a page table walk step, a store buffer writeback).
Each transition affects the state (e.g., a memory access reads or updates the value in a memory cell) and an enabling condition is required (e.g., for a memory access to be permitted, there must be a corresponding entry in the TLB).
\hl{Our initial model was based on documentation and assumptions made by existing operating systems. This model is then iteratively tested and improved if necessary.}


\noindent\textbf{Model Reduction (\Cref{sec:reduction})}
%
We reduce our considered model guided by the small-scope hypotheses~\cite{Jackson:2002:Alloy}. The small scope hypothesis anticipates that most behaviors observable in a given system are expected to be seen in a smaller scope. \hl{In our context, given the hardware model, we make the reasonable assumption that a calculated bounded (on parameters like number of cores, virtual and physical memory addresses, page table levels etc)  testing environment would suffice to expose most behaviors of relevance.} While not formally proven, this assumption is standard in testing and bounded model checking \hl{and can guide induction based proofs}. 
The hardware model must accurately represent the underlying hardware platform. 
For an x86 multi-core machine, this means all its cores, 64-bit memory, 5-level paging, etc. 
The resulting state space is enormous.
Fortunately, there are many symmetries we can exploit to reduce the state space. 
For example, while multi-core machines can have several hundred cores, we might only need to consider a handful of cores to expose unique hardware behavior.
\hl{Many of the simplifications we make in the current stage correlate strongly to the x86 hardware but reduction arguments can be adapted appropriately to the corresponding model of interest.}

\noindent\textbf{Test Case Generation (\Cref{sec:testgen})}
Based on the reduced hardware model, we automatically generate diverse test programs, i.e., per-core sequences of instructions that provide the trace of externally visible program steps that expose interesting hardware behavior.
This is similar to a fuzzer generating inputs to a program under test. 

\noindent\textbf{Test Execution Harness (\Cref{sec:harness})}
We execute the test programs on real hardware,
producing an execution trace that includes the instruction and the observable outcome, i.e., the value of the memory cell or that a fault occurred.
The challenge here is how to synchronize cores and store the instruction's result without affecting the outcome of future tests.
The observed values should reflect hardware translation and caching effects rather than interference from the operating system. 

\noindent\textbf{Trace Validation (\Cref{sec:analysis})}
To validate the collected execution trace, we must extend it with internal microarchitectural steps so that the outcomes of the observable steps are justified, e.g., the page walk succeeded.
We search for a sequence of model transitions that embeds the collected execution trace. 
A failed search indicates a model bug.
We cast this as a software synthesis problem: complete a program sketch by inserting the necessary internal steps.

A failed search indicates that no model-admissible execution exists for that observation, which is evidence that the model is incorrect or incomplete and can direct improvements.
