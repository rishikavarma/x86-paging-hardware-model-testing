\section{Trace Validation with Software Synthesis}\label{sec:analysis}
%% ============================================================

To validate whether the execution trace matches the model, we need to find a sequence of model transitions that explains the trace's observed behavior. 
Recall that the model's transitions fall into observable and internal steps, where the observable steps correspond to the behavior of the execution trace. 
We observe that we can treat the model's state transitions as possible steps a program takes.
In our case, this lets us cast the problem of trace validation as finding the missing internal steps that complete the observed trace from the execution. In other words, applying software synthesis to repair the trace by patching missing steps, a process similar to sketching~\cite{Solar-Lezama:2006:Sketching}.


\noindent\textbf{The Synthesis Problem.}
\emph{Given the model and an observable trace, we ask a solver to find a sequence of internal actions that, interleaved with the observed externals, is admissible by the model.}
A satisfying solution is a witness execution containing the internal actions that explain the observation; an unsatisfiable query indicates that no model-admissible execution explains the trace, and is evidence that the model is incorrect or incomplete. 


\noindent\textbf{Synthesis Implementation.}
We encode the synthesis problem in Rosette~\cite{Torlak:2013:Rosette} as a set of constraints over a single linear trace that interleaves the actions of all cores. 
\autoref{lst:analysis:rosette} shows the code, which consists of the following elements:

\begin{enumerate}[topsep=0pt, leftmargin=1.5em]
 \item \emph{System State.} One-to-one encoding of the model's state in Rosette.
 \item \emph{Grammar.} We define a grammar with a rule for each transition in the reduced model. 
 \item \emph{Interpretation.} Defines the grammar semantics equivalent to the model transitions. If a step would not be permissible, the interpretation yields the failed state; otherwise, it updates the system state according to its semantics.
 \item \emph{Program Correctness.} A candidate program is correct if it contains the observed external actions in the same order and with the same outcomes as in the execution trace.
\end{enumerate}
Rosette then uses the grammar to construct candidate programs, initializes the system state, starts interpreting the program, and uses the correctness condition to check whether the program satisfies the trace.

\begin{lstfloat}[t]
\begin{lstlisting}[
  basicstyle=\ttfamily\tiny,
  numbers=left,
  numberstyle=\tiny,
  numbersep=3pt,
  xleftmargin=1.4em,
  frame=single,
  framerule=0.0pt,
  breaklines=true,
  breakatwhitespace=true,
  columns=fullflexible,
  keepspaces=true
]
;; State: reduced MMU components.
(struct State (mem root pt tlb walks cache sbuf))

;; Model transition relation.
(define (step st op) ...) ; returns (state, valid?)

;; Grammar: candidate linear traces.
(define-grammar (trace-grammar)
  [tr (choose (Return) (Seq (op) (tr)))]
  [op (choose (OpMemOp c va r)
              (OpWritePTE c pa pte)
              (OpWriteback c)
              (OpInvlpg c va)
              (OpWalkNext c w)
              (OpTLBFill c w)
              ...)]
  [c   (choose 0 1 2)]
  [va  (choose VA0 VA1 ...)]
  [pa  (choose PA0 PA1 ...)]
  [pte (choose #f (cons pa valid?))]
  [w   (choose walk0 walk1 ...)])

;; Interpretation: validity is the conjunction
;; of all chosen model steps.
(define (interp tr st)
  (match tr
    [(Return) (values st #t)]
    [(Seq op rest)
     (define-values (st1 ok1) (step st op))
     (define-values (st2 ok2) (interp rest st1))
     (values st2 (and ok1 ok2))]))

;; Correctness constraint used by synthesis.
(define (check observed)
  (define tr (trace-grammar))
  (assert-required-ops tr observed)
  (define-values (_ ok) (interp tr (make-check-state)))
  (assert ok))

(synthesize #:guarantee (check observed-trace))
\end{lstlisting}
\caption{Simplified Rosette encoding for trace validation. The grammar expresses a linear sequence of model actions; the correctness condition mandates the ordering of observed events and asserts that the model accepts the interpretation.}
\label{lst:analysis:rosette}
\end{lstfloat}

\noindent\textbf{Challenges.}
Scalability is a challenge in software synthesis, as the number of choices grows exponentially with program length. While our current prototype can handle small scenarios (i.e., finding a handful of missing internal actions), scaling it to larger ones requires additional work -- and this despite the reduced model.
Currently, we do not impose structure or ordering on the internal steps; instead, we let Rosette determine them during synthesis. While this does not limit possible interleavings, it also adds complexity.
We think that a multi-step approach offers a promising improvement. Specifically, we plan to:

\begin{itemize}[topsep=0pt, leftmargin=1.5em]
  \item \emph{Abstract non-test cores.} Currently, we model all cores with the same fidelity. 
  This means Rosette must implement internal steps for all cores, which increases complexity.
  We plan to treat memory write-backs as relevant events and abstract away all internal steps for the other cores. 
  \item \emph{Big-Step Walks.} The model expresses page walks as multiple small steps; instead, we can introduce a complete walk as a grammar element, interleaved by possible page-table updates from other cores.
  \item \emph{Leveraging Domain Knowledge.} We observe that a memory access can only succeed if there is a corresponding TLB entry, which in turn can only be there if a page walk succeeded. We can leverage this dependency during synthesis. 
\end{itemize}
