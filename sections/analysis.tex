\section{Trace Validation with Software Synthesis}\label{sec:analysis}
%% ============================================================

To validate whether the execution traces match the model, we need to find a sequence of model transitions that explain the traces' behavior. 
Recall that the model's transitions fall into observable and internal steps, where the observable steps correspond to the behavior of the execution traces. 
While for short traces, this is easily achieved by manual analysis, we expect situations with long traces with many internal steps or a large number of traces to be analyzed.

We observe that we can treat the model's state transitions as the possible steps a program can take.
In our case, this lets us cast the problem of trace validation into a program completion problem: we need to find the missing internal steps and combine the observed traces from the execution into a single sequence. In other words, the problem we are facing is similar to ``repairing'' the traces by patching missing steps and combining, a process similar to sketching~\cite{Solar-Lezama:2006:Sketching} 
or program repair~\cite{Nguyen:2013:SemFix} in the context of software synthesis. Thus, we cast trace validation as a software synthesis problem.

\noindent\textbf{The Synthesis Problem.}
\emph{Given the model and an observable trace set, we ask a solver to find a combined sequence of internal actions interleaved with the observed external events, that is admissible by the model.}
\end{tcolorbox}

A satisfying solution is a witness execution containing the internal actions that explain the observed outcomes of the test program. An unsatisfiable query indicates that no model-admissible execution can explain the traces and is evidence that the model is incorrect or incomplete. 

\noindent\textbf{Synthesis Implementation.}
We encode the synthesis problem in Rosette~\cite{Torlak:2013:Rosette} as a set of constraints over a single linear trace that interleaves the core's actions. 
\autoref{lst:analysis:rosette} shows the simplified encoding consisting of the following elements:

\begin{enumerate}[topsep=0pt, leftmargin=1.5em]
 \item \emph{System State.} One-to-one encoding of the model's state in Rosette, i.e., memory, per-core TLBs, caches, etc. 
 \item \emph{Grammar.} Defines a grammar from which the trace is completed. It contains a rule for each model transition. 
 \item \emph{Interpretation.} Defines the grammar semantics equivalent to the model transitions. If a step would not be permissible, the interpretation yields the non-updated state with an indication of failure; otherwise, it updates the system state according to its semantics.
 \item \emph{Program Correctness Predicate.} A candidate program is correct if it contains the observed external actions in the same order and with the same outcomes as in the execution trace.
\end{enumerate}
Rosette then uses the grammar to construct candidate programs, initializes the system state, starts interpreting the program, and checks whether the program satisfies the trace using the correctness condition.

\begin{lstlisting}[
  basicstyle=\ttfamily\scriptsize,
  numbers=left,
  numberstyle=\tiny,
  numbersep=3pt,
  xleftmargin=1.4em,
  frame=single,
  framerule=0.0pt,
  breaklines=true,
  breakatwhitespace=true,
  columns=fullflexible,
  keepspaces=true
]
;; State: MMU components.
(struct State (mem root pt tlb walks cache sbuf))

;; Model transitions modifying state
(define (step st op) ...) ; returns (state, valid?)

;; Grammar: candidate linear traces.
(define-grammar (trace-grammar)
  [tr (choose (Return) (Seq (op) (tr)))]
  [op (choose (OpMemOp c va r)
              (OpWritePTE c pa pte)
              (OpWalkNext c w)
              (OpTLBFill c w) ...)]
  [c   (choose 0 1 2)]
  [va  (choose VA0 VA1 ...)]
  [pa  (choose PA0 PA1 ...)]
  [pte (choose #f (cons pa valid?))]
  [w   (choose walk0 walk1 ...)])

;; Interpretation: Semantic definition of steps
(define (interp tr st)
  (match tr
    [(Return) (values st #t)]
    [(Seq op rest)
     (define-values (st1 ok1) (step st op))
     (define-values (st2 ok2) (interp rest st1))
     (values st2 (and ok1 ok2))]))

;; Program Correctness Predicate.
(define (check observed)
  (define tr (trace-grammar))
  (assert-required-ops tr observed)
  (define-values (_ valid) (interp tr (make-check-state)))
  (assert valid))

(synthesize #:guarantee (check observed-trace))
\end{lstlisting}
\caption{Simplified Rosette encoding for trace validation. The grammar expresses a linear sequence of model actions; the correctness condition mandates the ordering of observed events and asserts that the model accepts the interpretation.}
\label{lst:analysis:rosette}
\end{lstfloat}

\noindent\textbf{Challenges.}
The synthesis problem grows exponentially in trace length and grammar size.
While our current prototype can handle small scenarios (i.e., finding a handful of missing internal actions), scaling it to larger ones requires additional work. 
Our model reduction technique has proven useful in this regard. 
However, there are still some opportunities to further reduce the choices.
For example, we do not currently impose structure or order on the internal steps. Instead, we let Rosette determine them during synthesis. While this includes all possible interleavings, it also produces traces that would not occur in hardware, e.g., filling the TLB before a corresponding page walk completes. The core challenge here is to over-constrain the grammar.

A multi-step synthesis approach offers a promising path. Specifically, we plan to:

\begin{itemize}[topsep=0pt, leftmargin=1.5em]
  \item \emph{Abstract non-test cores.} Currently, we model all cores with the same fidelity, as we have not implemented the core-fidelity reduction yet (\S\ref{sec:reduction}).
  Consequently, Rosette must handle internal steps for all cores, which increases complexity.
  We plan to abstract away all internal steps for the other cores. 
  \item \emph{Use Big-Step Walks.} The model expresses page walks as multiple small steps. Instead, we can introduce a complete walk as a grammar element, interleaved by possible page-table updates from the local or other cores.
  \item \emph{Leverage Domain Knowledge.} We observe that a memory access can only succeed if there is a corresponding TLB entry, which in turn can only exist if a page walk succeeded -- a dependency we can leverage. 
\end{itemize}
