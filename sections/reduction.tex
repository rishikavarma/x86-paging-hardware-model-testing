
\section{State Reduction}\label{sec:reduction} %%

To make test generation and validation tractable, we reduce the hardware model by limiting the range of values for various aspects of the model. 
Next, we present several model state reductions we applied, along with informal arguments \hl{justifying each reduction. While all aspects are specific to the x86 multi-core model, we expect similar arguments to be applicable to other hardware models.}
While these justifications are not rigorous proofs, they are a principled application of a small-scope hypothesis~\cite{Jackson:2002:Alloy} that states that most behaviors observable in a given system are likely to be observed at a smaller scope as well. Specifically, by constraining the domain of values in a principled way, we can still observe the relevant hardware behavior.

\noindent\textbf{Core Fidelity.} 
On a multi-core system, cores typically share memory and might even use the same page table for multi-threaded processes.
However, we observe that any given core does not directly see the internal steps of the other cores in the system.
Instead, each core only sees write-back events from other cores.
Hence, we do not need to model all cores with full fidelity \hl{at the same time}. Instead, we can pick \hl{each core separately} as the ``core under test'' and reduce the other cores to execute a sequence of memory writebacks that can happen at any time in the trace. \hl{This breakdown preserves the overall fidelity of all cores while simplifying analysis.}


\noindent\textbf{Two cores.}
By reducing the core fidelity, we can make a second observation: 
From the "core-under-test's" point of view, it does not matter which other core executed the memory writeback. What matters is the order in which the core observes them.
This enables us to merge writebacks from other cores into a single writeback sequence, where the non-deterministic ordering results in a permutation of the order. 
Assuming a multicopy atomic update architecture~\cite{Coughlin:2023:NonMultiCopyUpdates} such as x86, we can reduce the \hl{total arbitrary core count to two representative cores}: the core under test and a single "remote" core that executes all writebacks of the other cores in the system.


\noindent\textbf{Two Levels of Paging.}
The x86 architecture has up to five levels of page tables that store the virtual-to-physical address translation. 
We note that for a page walk to resolve to the wrong address, any wrong step while traversing the page table, including using the page walk caches, is sufficient. 
The critical aspect here is that we need to model the non-atomicity of a page table walk. Specifically,  we must 1) capture the effect of the page walk caches that skip the upper levels of the page table on the page walk, 2) include potential behaviors resulting from interleavings between page table writes and page walks, and 3) expose the effect of super pages in the mapping. 

Selecting only the lowest two levels (PMD and PT in Linux terms) for modification, and keeping the remaining levels fixed, lets us expose the necessary behavior: the page walk is non-atomic because it reads the PMD and PT entries in two steps. 
Further, a page table walk may directly or indirectly use the old value of the PMD entry by skipping it entirely via the page walk cache, or by reading the PMD entry before it was updated (cases 1 and 2). Similarly, on x86, super pages are established at the PMD level, and thus the two levels are sufficient to expose changing of page sizes (case 3). Other behaviors at upper-level page table nodes or other superpage sizes can be mapped to a similar sequence of steps on the two-level setup.


\noindent\textbf{Three Virtual Pages (or PTEs).}
Each virtual page maps to a specific leaf-level page table entry. Each virtual page has a distinct path that the page table walker takes during address translation. The important factor here is the shared prefix. While we can consider paths that diverge at the root largely independent, paths that share a prefix are of interest as they will populate the page walk caches. Hence, the common prefix of the path might be skipped due to those caches.
We select three virtual pages: two on the same PT page and one on a different PT page, covering the earlier prefix divergence.


\noindent\textbf{Four Virtual Addresses.}
The x86 MMU does not translate at the byte level; instead, it operates at the page granularity. Given that we reduced the number of virtual pages to three, we should select one representative address of each page. In addition, we add one additional address on one of the pages, exposing a TLB-cached virtual-to-physical mapping.

\noindent\textbf{Four Physical Frames.}
These are the corresponding physical memory frames that the virtual pages map to. Here, we must be able to remap an existing mapping of the virtual pages without creating an alias. Hence, we need to use one more physical frame than we use virtual frames.
