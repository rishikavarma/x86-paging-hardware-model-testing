
\section{State Reduction}\label{sec:reduction} %%

To make test generation and validation tractable, we reduce the hardware model by limiting the range of values for various aspects
guided by a small-scope hypothesis~\cite{Jackson:2002:Alloy}.
Next, we present each aspect of the model along with tentative informal arguments \hl{applicable to our model justifying each reduction. While all aspects of this reduction may not be generalizable, similar relevant arguments can be made for any other hardware models.}
While these are not rigorous proofs, they are a principled application of a small-scope argument where behaviors are expected to have small witnesses, and can be used to guide formal proving. 

\noindent\textbf{Two cores.}
On a multi-core system, cores share memory and even use the same page table. At first, this means we cannot reduce the number of cores. 
Fortunately, the internal transitions are core-local and not directly observable by other cores. Instead, other cores observe a sequence of memory accesses that originate either from the program's load/store instructions or from a core's internal steps. This provides an opportunity, from a specific core's point of view, it does not matter which other core emitted the memory access. Thus, we can merge the memory accesses of other cores into a single memory access sequence where the non-deterministic ordering results in a permutation of that order. Thus, we can reduce the number of cores to two. \hl{While there are documented behaviours which cannot be observed with two cores (eg: Non-multicopy atomic), these are hardware specific and the reduction needs to be adapted based on the hardware type. In the case of x86 (which allows multi-copy atomic) we expect 2 cores to be sufficient. }

\noindent\textbf{Core Fidelity.} 
Using the observation above, we do not need to model all cores with full fidelity. Instead, we can reduce the second core to a sequence of memory writebacks that can happen at any time in the trace.

\noindent\textbf{Two Levels of Paging.}
The x86 architecture has up to five levels of page tables that store the virtual-to-physical address translation. 
The critical aspect here is that \hl{we need to} model the non-atomicity of a page table walk. Specifically,  
we \hl{need our model to 1) capture the} effect of the page walk caches that skip the upper levels of the page table on the page walk, 
\hl{2) include potential behaviors resulting from interleavings between page table writes and page walks}, and
3) expose the effect of super pages in the mapping. 
\hl{For the first case, it is sufficient for a testing environment where page walk caches skip one level and jump directly to the leaf level containing the physical page's address. Invoking interleavings also only requires atleast 2 levels to expose subsequent effects. Similarly, superpages change the entry type of an upper-level page table so that it now contains the page's physical address rather than pointing to the next level. This can also be achieved with two levels.}


\noindent\textbf{Three Virtual Pages (or PTEs).}
Each virtual page maps to a specific leaf-level page table entry. Each virtual page has a distinct path that the page table walker takes during address translation. The important factor here is the shared prefix. While we can consider paths that diverge at the root largely independent, paths that share a prefix are of interest as they will populate the page walk caches. Hence, the common prefix of the path might be skipped due to those caches.
We select three virtual pages: two on the same PT page and one on a different PT page, covering the earlier prefix divergence.


\noindent\textbf{Four Virtual Addresses.}
The x86 MMU does not translate at the byte level; instead, it operates at the page granularity. Given that we reduced the number of virtual pages to three, we should select one representative address of each page. In addition, we add one additional address on one of the pages, exposing a TLB-cached virtual-to-physical mapping.

\noindent\textbf{Four Physical Frames.}
These are the corresponding physical memory frames to which the virtual pages map. Here, we must be able to remap an existing mapping of the virtual pages without creating an alias. Hence, we need to use one more physical frame than we use virtual frames.
